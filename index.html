Illustration of my workflow

Quality starts before the first test case.

I start with the requirements. Before testing anything, I read the SRS, go through the business workflow, and work out what each role should and shouldn’t be able to do. Then I compare that with what the system actually does. Where the two don’t match is usually where the important issues are.

Then comes the testing: I write scenarios, test end to end, and check the APIs in Postman. When I find a defect, I document it so a developer can reproduce it without asking me. I retest the fix, run regression, and support UAT until the release is ready. Throughout, I work closely with developers, project managers, and the client.

How I test

The testing cycle at the top shows the stages. This is the thinking inside them: the question I keep asking at each point.

  1. 01

    Understand the rule

    What should happen, and why?

    I read the business rule behind a feature, not only the screen.

  2. 02

    Map the roles

    Who can do this, and who must not?

    Every role the flow touches, including the ones that should be blocked.

  3. 03

    Cover the paths

    What happens off the happy path?

    Negative paths, boundaries, and edge cases like the last seat or a double submit.

  4. 04

    Check every layer

    Where does the issue really live?

    The UI, the API response, and the integration between them.

  5. 05

    Leave evidence

    Can a developer reproduce this alone?

    Steps, data, actual vs expected, and screenshots or responses.

  6. 06

    Weigh the impact

    What else could this change break?

    Verify the fix in context, run regression, and confirm release readiness.

Preconditions

  • learner1@northfield-learning.test and learner2@northfield-learning.test are registered, so the course is full (2 of 2).

Steps to reproduce

  1. Sign in as learner1@northfield-learning.test.
  2. Go to My Courses and open Intro to Data Literacy.
  3. Click Cancel registration and confirm in the dialog.
  4. Check that the course now shows the status Cancelled in My Courses.
  5. Sign out, then sign in as learner3@northfield-learning.test.
  6. Open the course page for Intro to Data Literacy.
  7. Look at the seat counter and the Register button.

Result

Actual result

The course page shows "Course full (2/2)" and the Register button is disabled. The same count appears after a hard refresh.

Expected result

The course page shows 1 of 2 seats taken and the Register button is enabled, as the cancellation should release the seat (BR-05).

Requirements validation: registration deadline

Northfield Learning Portal SRS v1.3, fictional

Requirement
REQ-REG-07
Result
Not met
Findings
1 defect, 1 clarification

Demonstration sample. Created for this portfolio with fictional data to show my QA documentation style. It is not taken from any client project.

  1. RequirementREQ-REG-07Block registration after the deadline
  2. ImplementationUI and APIButton hidden, API still accepts
  3. QA validationTS-CR-03Tested through UI and API
  4. FindingNot metDefect and clarification raised

Documented requirement

REQ-REG-07"The system shall prevent registration after the registration deadline."

Test condition

Course CRS-DEMO-311 has its registration deadline set to 15 March 2026, 23:59. A learner attempts to register at 16 March 2026, 00:05, first from the course page and then with a direct POST /api/v1/registrations request.

Behavior

System behavior

The course page hides the Register button, which is correct. The direct API request returns 201 Created and a confirmed registration is saved after the deadline.

Expected behavior

Registration is refused at every entry point. The API returns 422 REGISTRATION_CLOSED and no record is created.

Findings

F-1: Implementation defect

The deadline is enforced in the UI only. The backend does not validate it, so the requirement is not met.

F-2: Requirement gap

The SRS does not state the deadline's time zone, or whether registrations exactly at 23:59 count. Two readings of the requirement are possible.

Impact

Learners can register after the deadline through the API, a cached page, or an open browser tab. Late registrations affect seat counts and session planning, and they conflict with what the client expects the system to do.

QA decision

  • Mark REQ-REG-07 as Not met in the traceability record.
  • Log defect BUG-DEMO-0157 for backend deadline validation, with the API request and response as evidence.
  • Raise a clarification with the business analyst and the client on the time zone and on whether 23:59 is inclusive.
  • After the fix: retest through UI and API, then run regression on registration, cancellation, and seat counts.
